Sortable list – Manual – Live Wires

Sortable list

Reorder items with a drag handle, move buttons, or the keyboard. The list keeps its order until the application confirms a move.

Fixture

This page simulates application responses. It does not contact a server. The list stays put until an accepted response updates its markup. Rejected and unrelated updates leave its order unchanged.

What to exercise

  • Use keyboard staging: focus a handle, press Space, use arrow keys, then Space to request or Escape to cancel.
  • Drag a handle with a pointer or touch input. The component marks a destination but leaves authoritative order unchanged.
  • Choose accept or reject before requesting a move. Try an unrelated update while pending; only the matching explicit result clears pending state.
  • Start a delayed move, remove and reinsert List A, then wait. Its old response must not reorder the reconnected list.
  • During a delayed accepted move, move focus to the external button. The result must not steal focus back into the replaced list.
  • Use both lists to confirm pending state and result IDs remain isolated. Try the nested link and a narrow viewport.
  • On a touch device, drag the handle. With reduced motion enabled, check that the source and destination cues remain visible without movement animation.

When you stage a move, the source lifts into view and the destination rule sweeps into place. These cues show the requested position while the authoritative list stays unchanged. The fixture records adapter-listener duration separately from the response timer, then records markup/result handling and a two-frame observation. It does not measure the component’s input handler or guarantee paint timing; formal handler and paint measurements remain pending the maintained browser target.

Update contract

The consumer owns authorization, persistence, ordering and retries. It handles sortable-move-request, applies the authoritative server response, then calls resolveMove with the same request ID. The fixture represents the delayed response as a separate fixture-sse-update event and checks connection generation and request ID before replacing any list markup. Unrelated patches do not acknowledge requests.

HTML hooks are data-sortable-list, data-sortable-item, data-item-id, data-sortable-handle, data-sortable-move and data-sortable-status. CSS marks staged sources and targets with data-sortable-source and data-sortable-target, and pending state on the custom element. Disconnect cancels transient interaction and invalidates its pending ID; reinsertion installs one listener set.

Build measurements

Run the dependency-free contract checks with node --test tests/sortable-list-state.test.js. In this build, the optional JavaScript is 10,875 bytes raw (3.37 kB gzip) and the CSS is 6,031 bytes raw (1.30 kB gzip). The default main.js and main.css still match the base byte-for-byte.

One local browser sample on 2026-10-09 used Firefox 153 and Playwright WebKit 26.5 at 1440×900 with a separate 100 ms fixture delay. The host capture-to-bubble event path (component plus synchronous request adapter) took 0–1 ms for keyboard and pointer input in Firefox, and 0–7 ms in WebKit. Authoritative DOM/result updates took 1–2 ms in Firefox and 1 ms in WebKit. The following two-frame observation took 9–14 ms in Firefox and 25–31 ms in WebKit. These are single-run diagnostics, not benchmarks; the two-frame value is not a direct paint measurement. Chromium, real touch input, reduced-motion emulation, and direct paint timing were not verified.

After the visual update, Firefox and WebKit both rendered the component sidebar without horizontal overflow at 320, 375, 768 and 1,440 CSS pixels. In WebKit, keyboard staging activated the source and destination CSS animations while preserving list order; the fixture then applied a delayed accepted response and the item moved to its confirmed position. Reduced-motion emulation, Chromium, real touch and direct paint timing were not checked in this visual pass.
